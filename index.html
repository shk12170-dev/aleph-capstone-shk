보안 관제 · 자동 대응 프로젝트 ALEPH

가상 공공기관 해담시청의 민원포털을 대상으로, 공격을 찾아 자동으로 막고 정상 사용자는 계속 쓸 수 있는지 직접 시험했습니다. 저는 경보·기록 담당(C)으로 Wazuh와 보안 대시보드를 만들고, 최종 발표에서 S8 케이스를 시연했습니다.

역할

4인 팀의 PC 4대 중 경보·기록 PC를 맡았습니다. 탐지는 Graylog, 자동 조치는 n8n이 하고, 저는 그 결과를 사건 하나의 흐름으로 모아 확인하는 쪽을 책임졌습니다.

  • Wazuh: 포털 서버 에이전트의 경보를 모아 Graylog로 전달하는 경로 구성
  • 보안 대시보드: 티켓 저장소, API, 사건 목록·상세 화면을 직접 구현
  • S8 시연: 11/6 최종 발표에서 S8과 대시보드 파트를 7분 30초간 발표

S8 구현·검증

페이지를 훑고 로그인을 시도한 출발지를 막았습니다

같은 출발지에서 15분 안에 없는 페이지 탐색(404)과 로그인 실패(401)가 함께 나오면 침입 시도로 보고, 포털에서 그 출발지의 접근을 차단합니다. 페이지 주소를 한 번 틀린 것만으로는 막지 않도록 서로 다른 두 신호를 묶었습니다.

  1. 1 공격Kali에서 스캔·로그인 시도
  2. 2 탐지Graylog 규칙 (포털 로그)
  3. 3 대응n8n이 포털 IP 차단
  4. 4 확인재접속 403, 정상 200
  5. 5 기록티켓 생성, 사람이 해제·종료

11/03 성공 회차에서 마지막 입력부터 포털 차단까지 37.9초가 걸렸습니다. 차단 뒤 공격 출발지는 403, 정상 출발지는 로그인과 민원 목록 200으로 확인했습니다. 해제는 사람이 연결했고, 해제 뒤 재접속 200도 확인했습니다.

S8의 탐지 신호는 포털 로그입니다. Wazuh가 S8을 탐지한 것은 아닙니다.

문제 해결

탐지는 됐는데 차단이 안 됐습니다

첫 시도: 연결 실패탐지와 알림은 발생했지만 n8n에 자동 대응을 받을 웹훅 주소가 등록되지 않아 차단과 티켓으로 이어지지 않았습니다.
수정 후: 효과 확인연결 경로를 다시 등록하고 실제 차단, 정상 접근, 해제 뒤 재접속까지 같은 흐름을 끝까지 실행해 확인했습니다.

이 실패는 공격을 놓친 미탐이 아니라 대응 연결 실패로 분류했고, 정량평가 분모에 그대로 넣었습니다. 이후 확인 방식을 탐지 화면만 보지 않고 조치와 사건 기록까지 대조하도록 바꿨습니다. S8은 이 첫 실패를 포함해 2건 중 1건 성공으로 집계했습니다.

보안 대시보드

사건의 처리 과정을 한곳에 모았습니다

  • 사건 찾기: 계정·출발지·케이스로 어떤 사건인지 확인
  • 효과 구분: 조치 명령의 성공과 실제 차단 결과를 따로 표시
  • 남은 회복 확인: 해제되지 않은 조치와 사건 종료 조건 점검

티켓을 닫는 것은 기록의 종료일 뿐이며, 실제 복구는 따로 확인합니다. 대시보드는 직접 차단 해제나 비밀번호 재설정을 실행하지 않고, 탐지는 Graylog, 대응은 n8n이 맡도록 역할을 나눴습니다. 발표에 쓴 화면은 구조 설명용 합성 예시이며 실측 수치가 아닙니다.

Wazuh

포털 서버의 경보를 Graylog로 보냈습니다

포털 서버 에이전트의 경보를 모아 Graylog로 전달하는 경로를 구성했습니다. 1,400바이트가 넘는 UDP 전송이 유실되는 원인을 크기별 시험으로 찾아 TCP 중계로 해결했습니다. 파일 변경 감시는 S7에서 활용했습니다.

이번 네 케이스(S1·S4·S8·S10)의 주된 판단 신호는 포털 로그와 pfSense 기록이며, Wazuh가 탐지한 것은 아닙니다.

한계와 다음 과제

  • S8 결과는 11/03 회차 기준의 작은 표본이며 실제 운영 성공률을 뜻하지 않습니다.
  • 차단 해제는 모두 사람이 연결했습니다. 자동 원복은 확인하지 못했습니다.
  • S7(홈페이지 변조)은 탐지 티켓과 수동 복구 시험까지만 확인했고, 자동 복구는 켜지 않았습니다.
  • 정상 사용자 장시간 시험과 경계 시험은 미완료라 오탐률을 단정하지 않았습니다.
