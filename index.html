① 팀 프로젝트

경보·기록 PC(C)를 맡았습니다

  • Wazuh: 포털 서버의 경보를 Graylog로 전달. 1,400바이트가 넘는 UDP 경보가 사라지는 문제를 TCP 중계로 해결
  • 보안 대시보드: 티켓 저장소·API·사건 목록과 상세 화면 구현. 조치 성공과 실제 차단 효과를 따로 표시
  • S8 시연: 15분 안에 같은 출발지에서 404와 401이 겹치면 포털 차단. 11/03 성공 회차에서 마지막 입력부터 차단까지 37.9초, 공격자 403·정상 사용자 200 확인
첫 시도: 연결 실패탐지는 됐지만 n8n 웹훅 주소가 등록되지 않아 차단과 티켓으로 이어지지 않았습니다.
수정 후: 끝까지 확인연결을 다시 등록하고 차단·정상 접근·해제까지 확인했습니다. 첫 실패도 숨기지 않고 1/2로 집계했습니다.

팀에서 S7(홈페이지 변조)은 수동 복구 시험까지만 했고, 차단 해제는 사람이 했습니다. 이 빈칸이 개인 재구성의 출발점이 됐습니다.

② 1인 재구성

haedam-soar-portfolio

팀 4대 구성을 PC 한 대에 그대로 세웠습니다

pfSense 가상 방화벽(네트워크 카드 4개)과 OpenVPN을 직접 구성하고, 포털·DB 가상 PC를 무인 설치하고, Graylog·n8n·Wazuh·티켓 저장소를 Docker로 띄웠습니다. 팀과 같은 주소와 같은 VPN(10.250.0.0/24) 구조를 유지해서, 팀원 4명의 역할을 혼자 모두 거쳐 봤습니다.

S1 실측: 조건이 채워진 뒤 차단까지 약 3.7초, 차단 뒤 효과 확인까지 38초였고 정상 사용자 오차단은 0건이었습니다. 팀에서 끝내지 못한 Wazuh 자동 복구(S7)를 이번에 설치·등록해, 변조된 파일은 원본으로 되돌리고 새로 심은 파일은 격리하는 것까지 확인했습니다.

문제 해결

  • 켜는 순서에 따라 멈춤: VPN보다 Docker가 먼저 뜨면 VPN 주소에 묶인 Graylog·Wazuh가 멈췄고, pfSense보다 VPN이 먼저 뜨면 300초를 기다렸습니다. pfSense → VPN → Docker → 가상 PC 순서를 정해 문서로 남겼습니다.
  • S4 첫 회차 전부 403: 공격 스크립트가 로그인 보안 확인(CSRF) 절차를 빠뜨려 이벤트가 하나도 생기지 않았습니다. 그 회차는 버리고 스크립트를 고쳐 다시 실행했습니다.
  • 다음 회차 알림이 안 옴: Graylog의 재알림 대기 시간(30분)이 사람별이 아니라 규칙 전체에 걸리는 것을 확인하고 시험 간격을 다시 계획했습니다.
  • Wazuh 설정 거부: 자동 복구 설정 값(specific)이 4.9 버전에서 거부되는 원인을 찾아 local로 고치고, 재설치해도 남도록 저장소에 반영했습니다.
  • 비밀값 유실: Windows 업그레이드로 코드 폴더가 지워져 저장소에 없는 .env가 사라졌습니다. 실행 중인 컨테이너에서 값을 되살렸고, 지우기 전에 저장소 밖에 복사해 두는 규칙을 세웠습니다.

한계와 다음 과제

  • pfSense 경계 차단은 설정까지는 됐지만 웹 연결을 실제로 끊지 못했습니다. 실제 차단은 포털 쪽에서 일어났습니다.
  • S7 티켓은 복구는 끝났지만 종료 조건이 맞지 않아 "확인됨"에서 멈춰 있고, S1·S4·S8·S10의 해제 기록은 사람이 남겼습니다.
  • S12는 안전한 부하 안에서만 시험해 실제로 서비스가 느려지는 상황의 차단·회복은 보지 못했습니다.
  • 케이스마다 실제 대응 회차는 1회씩이라 표본이 작고, 평소 설정은 실제 차단 대신 관찰 모드로 둡니다.
